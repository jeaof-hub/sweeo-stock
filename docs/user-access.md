Migration `08_role_matrix_and_audit.sql` ย้าย `editor` เป็น `warehouse` และ `viewer` เป็น `sales`. Migration `09_owner_admin_auditor.sql` ย้าย `manager` เป็น `admin` และ `sales` เป็น `auditor` พร้อมเพิ่มบทบาท `owner`. ผู้ก่อตั้งยังมีได้เพียงบัญชีเดียว และไม่มีใครจัดการบัญชีผู้ก่อตั้งผ่านเว็บได้

ฐานข้อมูลบังคับสิทธิ์อ่านและเขียนผ่าน Row Level Security. รายการที่ถูกลบจะยังอยู่ในฐานข้อมูล และแอดมิน/เจ้าของ/ผู้ก่อตั้งดูได้ในแท็บรายการที่ถูกลบ. ตาราง `stock_audit` บันทึกค่าก่อนและหลังการเพิ่ม/แก้/ลบสินค้าและรายการรับเข้า/ส่งออกจาก trigger ของฐานข้อมูล โดยเจ้าของและผู้ก่อตั้งอ่านได้. Log นี้เริ่มนับจากวันที่ติดตั้ง migration 08; ไม่สามารถย้อนสร้างเหตุการณ์ก่อนหน้าได้.

การลบในวันเดียวกันหมายถึงวันปฏิทินตามเขตเวลา `Asia/Bangkok` จากเวลาที่ระบบบันทึกรายการจริง ไม่ใช่วันที่ที่กรอกในเอกสาร. ฝ่ายคลังสินค้าลบได้เฉพาะรายการที่ `created_by` เป็นบัญชีของตนเอง.

ในช่วงเปลี่ยนผ่านของเฟส 1 คลังสินค้ายังบันทึกส่งออกโดยตรงและลบรายการของตนเองภายในวันเดียวกันได้ แต่บันทึกรับเข้าและปรับยอดไม่ได้ กติกาการส่งออกจะเปลี่ยนอีกครั้งในเฟส 2.

สมาชิกที่เปิดใช้งานทุกบทบาทเรียก `staff_display_names()` เพื่อแสดงชื่อผู้บันทึกได้ ฟังก์ชันนี้คืนเฉพาะ `user_id` และชื่อ. ผู้ตรวจสอบยังอ่านแถวบัญชีของตนเองใน `staff` ได้ ส่วนแอดมินและคลังสินค้าอ่านตาราง `staff` โดยตรงไม่ได้. เจ้าของเห็นและจัดการสมาชิกทุกคนยกเว้นผู้ก่อตั้ง.

การสร้างผู้ใช้และเปลี่ยนสิทธิ์ผ่าน Edge Function `manage-users` ตรวจตัวตนผ่าน Supabase Auth และตรวจว่า `staff.role` เป็น `founder` หรือ `owner` และบัญชียังเปิดใช้งานอยู่ทุกครั้ง. ห้ามสร้างบทบาท `founder` หรือเปลี่ยนสิทธิ์ ตั้งรหัสผ่าน หรือปิดบัญชีผู้ก่อตั้งผ่านเว็บ. เว็บไม่มี service-role key. ผู้ก่อตั้งหรือเจ้าของตั้งรหัสผ่านสมาชิกได้โดยไม่ส่งอีเมลเชิญ และควรแจ้งรหัสผ่านทางช่องทางส่วนตัว.

สมาชิกเข้าสู่ระบบด้วย Username หรืออีเมลโดยใช้รหัสผ่านเดียวกัน. การค้นหา Username ทำใน Edge Function `login-username`; หน้าเว็บไม่อ่านอีเมลจาก Username โดยตรง. ระบบใช้ข้อความผิดพลาดแบบเดียวกันเมื่อ Username ไม่มี บัญชีถูกปิด หรือรหัสผ่านผิด และจำกัดความถี่ตาม IP และชื่อที่กรอก.
